# Команда субагентов «Питомцы и дом»

Четыре специализированных субагента + главный агент-оркестратор. Почему четыре: у проекта
один внешний шов — операции чистого ядра `src/domain/` (ARCHITECTURE.md), поэтому ядро —
один агент (делить его — пересылка интерфейсов); оболочка естественно распадается на
хранение/стор и UI; приёмка вынесена за скобки, чтобы вердикт выносил не тот, кто писал код.

Живые определения агентов: `.zcode/agents/` (domain-core, storage-state, ui-craft,
qa-acceptance) — подхватятся сессией, открытой в корне проекта или worktree. Их системные
промпты — первоисточник; этот документ — чартер: матрица, контракт между агентами и процесс.

## Контракт между агентами

Единственная точка пересылки — операции ядра (`src/domain/`) и публичный API стора
(`store.tsx` + репозиторий). Их меняет только оркестратор: domain-core, которому
понадобилось расширить интерфейс, останавливается и докладывает — у двух других
агентов контракт лопнет.

```
ui-craft ──→ стор / репозиторий (storage-state) ──→ операции ядра (domain-core)
qa-acceptance ──→ прогоняет только то, что видит пользователь
```

## Особенность платформы: блокировка спавна

Спавн специализированного субагента иногда блокируется платформой. Отработанный обход
(прецедент — «Делим», тикет #07): спавнить `general-purpose` под явным чартером —
полный текст файла агента первым блоком промпта. Подробное описание — в
[WORKFLOW.md](WORKFLOW.md), раздел «Особенность: блокировка спавна платформой».

## Процесс

1. Оркестратор берёт из [tickets/](../tickets/README.md) фронт (блокаторы закрыты и
   смержены) и назначает первичного агента.
2. Агент работает в своём scope, гоняет vitest до зелёного, отмечает чекбоксы,
   переводит Status = done; тикет-сессия пушит ветку.
3. **После done — обязательная ревью-сессия code-review в новом окне** (см.
   [WORKFLOW.md](WORKFLOW.md)): прогон изменений ветки против merge-base с master
   по осям Standards и Spec. P1/P2 тикет-сессия исправляет до передачи PR; P3/P4 —
   в раздел «Замечания ревью» файла тикета.
4. Штаб открывает PR в GitHub (`#NN: <название>`); **сливает человек — «Squash and
   merge»**. Никаких прямых пушей в master.
5. Выход за scope или желание менять контракт — стоп и доклад оркестратору.
6. qa-acceptance подключается к закрытым экранам; его баги маршрутизирует оркестратор.
7. Оркестратор ревьюит соответствие ADR/GLOSSARY. После мержа — только подтянуть
   master (pull) и убрать worktree; пост-мерж-коммитов в master нет — статус
   тикета живёт в его файле (см. [WORKFLOW.md](WORKFLOW.md), «Конвенции»).
