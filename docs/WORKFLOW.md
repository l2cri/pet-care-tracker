# Workflow: git worktree + сессия на тикет + PR в GitHub со сквошем

Стратегия разработки: каждая тикет-сессия ZCode работает в отдельном git worktree
со своей веткой; готовый тикет уходит PR-ом в GitHub, ревью-сессия проверяет ветку,
а **сливает в master человек — кнопкой Merge со включённым squash** (один коммит
на тикет). Роли и зоны агентов — в [AGENTS.md](AGENTS.md), порядок тикетов —
в [tickets/README.md](../tickets/README.md).

Репозиторий: https://github.com/l2cri/pet-care-tracker

## Принципы

1. **Сессия = тикет = worktree = ветка.** Одна сессия закрывает один тикет и умирает.
   Никаких долгоживущих сессий «на весь проект».
2. **Параллелизм ограничен фронтом, а не числом рук.** Ветка тикета создаётся только
   после того, как все его блокаторы смержены в master (правило фронта из
   tickets/README). Максимальный реальный параллелизм этого DAG — 2 ветки
   (05–07 и 08/09 после 04). Больше worktree — не быстрее, а конфликтнее.
3. **Конфликты подавлены архитектурой.** Зоны агентов (domain / storage / app-UI)
   почти не пересекаются по файлам; всё, что пересекается, разведено блокирующими
   рёбрами.
4. **Master — только через PR со сквошем.** Прямых пушей в master нет. История
   master — один сквош-коммит на тикет: читаемый журнал вех. Внутренняя история
   сессии (красная/зелёная фаза, шаги) живёт в ветке PR — при желании её видно
   в PR, в master она не попадает.

## Роли

| Роль | Кто | Что делает |
|---|---|---|
| Штаб | сессия ZCode в главном чекауте `pet-care-tracker/` | смотрит фронт, создаёт worktree под тикет, открывает PR, подтягивает master после мержа (pull, без коммитов), ревьюит ADR-комплаенс |
| Тикет-сессия | сессия ZCode, открытая в папке worktree | главный агент сессии = владелец тикета по AGENTS.md; порождает субагентов, ведёт тикет до done, пушит ветку |
| Ревью-сессия | новая сессия ZCode в той же папке worktree, после done тикета | прогоняет скилл `code-review` по ветке против merge-base с master; отчёт P1–P4; ничего не правит и не мержит |
| Субагенты | domain-core / storage-state / ui-craft / qa-acceptance | работают внутри тикет-сессии по своим чартерам (см. особенность спавна ниже) |
| Вы | человек | создаёте сессии, смотрите отчёт ревью, **принимаете PR и жмёте Merge со включённым squash в master** |

`.zcode/agents/` закоммичен в репозитории → каждый worktree содержит определения
субагентов, сессия в worktree их видит.

## Особенность: блокировка спавна платформой

> Спавн заблокировался платформой (прецедент уже был в #07 — там выручил
> general-purpose под явным чартером). Повторяю так же.

Факт платформы: спавн специализированного субагента (`.zcode/agents/*.md`) иногда
блокируется — это не ошибка чартера и не повод переписывать агента. Отработанное
обходное решение (прецедент — «Делим», тикет #07): спавнить универсального агента
`general-purpose`, передав ему **явный чартер** — полный текст файла
`.zcode/agents/<имя>.md` вставляется в промпт спавна первым блоком, после чего
идёт задание. Чартер агента первоисточником не становится (системным промптом он
не является), поэтому в промпте явно сказано: «нижеследующий чартер — твои железные
правила; нарушать их нельзя». Всё остальное — зона, правила, готовность, стоп-условия —
работает как у нативного агента.

## Жизненный цикл тикета

```bash
# 0) Штаб: убедиться, что блокаторы тикета NN в master, затем
git worktree add ../pet-care-tracker-trees/t06 -b t/06-ics-export   # слог — латиницей

# 1) Открыть новую сессию ZCode в C:\Users\l2cri\Projects\pet-care-tracker-trees\t06
#    Промпт первого сообщения: «Работай по тикету tickets/06-ics-export.md,
#    ты — первичный владелец по docs/AGENTS.md, статус в in-progress»

# 2) Тикет-сессия: работа по чартеру, коммиты малыми шагами:
#    #06 domain: красная фаза — эталонные строки VCALENDAR
#    #06 domain: генератор VEVENT с RRULE и VALARM
#    #06 ui: кнопка календаря у пункта ухода
#    Чекбоксы тикета отмечаются по ходу; тесты — до зелёного.

# 3) Финал тикет-сессии:
git push -u origin t/06-ics-export
#    Status: done в файле тикета — последним коммитом ветки.

# 4) Штаб открывает PR в GitHub:
gh pr create --base master --head t/06-ics-export \
   --title "#06: Экспорт .ics" --body "<чек-лист приёмки тикета>"
#    (или кнопкой на странице репозитория)

# 5) РЕВЬЮ-СЕССИЯ — новая сессия ZCode в той же папке worktree. Промпт:
#    «Прогони code-review ветки t/06-ics-export против merge-base с master:
#    Standards — конвенции GLOSSARY/AGENTS/WORKFLOW, Spec — тикет 06
#    и docs/SPEC.md. Отчёт с приоритетами P1–P4; ничего не правь и не мержи».
#    P1/P2 — обязательны к исправлению до передачи PR человеку; P3/P4 —
#    в раздел «Замечания ревью» файла тикета (не блокируют мерж).

# 6) Правка приоритетных — в тикет-сессии (у неё контекст кода):
#    «исправь P1/P2 из отчёта ревью» → коммиты «#06 fix: ...» → тесты зелёные →
#    push → короткий перепрогон в той же ревью-сессии.

# 7) ВЫ: смотрите отчёт ревью и жмёте в GitHub Merge с включённым squash
#    (Delete branch — тоже жмём). Сквош-коммит: «#06: Экспорт .ics».

# 8) Штаб, после мержа:
git checkout master && git pull
git worktree remove ../pet-care-tracker-trees/t06
git branch -d t/06-ics-export
```

## Конвенции

- **Ветки**: `t/NN-slog-latincej` (например `t/05-care-timers`). Никакой кириллицы
  в именах веток и папок worktree — пути Windows вас поблагодарят.
- **Worktree**: `../pet-care-tracker-trees/tNN` — соседняя с репозиторием папка,
  вне репозитория.
- **Коммиты ветки**: `#NN <зона>: <что сделано>` — номер тикета обязателен, зона —
  domain/storage/ui/test/docs. Мелкие шаги приветствуются (красная/зелёная фаза —
  отдельные коммиты): в PR видно, как сессия думала; сквош в master съест детали —
  это осознанное решение (см. принцип 4).
- **PR**: заголовок `#NN: <название тикета>`, base master, описание — чек-лист
  приёмки из файла тикета. Мерж — только со включённым squash и удалением ветки.
- **Сквош-коммит master**: `#NN: <название тикета>` — по нему читается журнал вех.
- **Пост-мерж-коммитов нет.** Весь буккипинг (статусы тикетов, замечания ревью,
  правки доков) живёт в ветке тикета и попадает в master только его сквош-мержем.
  Отдельные «пост-мерж»-PR и коммиты (прецеденты #2, #5) запрещены: они конфликтуют
  с ветками в полёте (случилось: #5 против t/03). Статус тикета — только поле
  `Status:` в его файле, таблицы статусов в tickets/README.md нет.
- **Master**: всегда зелёный; GitHub Actions гоняет vitest на каждый пуш в ветки и
  master (настроен в тикете 01), Pages публикуется из master.

## Правила параллельности

1. Прежде чем создать worktree — проверь в tickets/README, что блокаторы тикета
   имеют Status: done **и** смержены (ветка садится на свежий master).
2. Держите ≤ 2–3 активных worktree. Фронт DAG всё равно не даст больше полезной работы.
3. Перед передачей PR человеку ветка обязана подтянуть свежий master и пройти тесты
   на результате (`git merge master` в ветке → vitest → push). Конфликт — сигнал,
   что рёбра DAG нарушены: разберитесь, а не «разрулите руками» молча.
4. Master никто, кроме GitHub-мержа человеком, не трогает: у worktree-сессий нет
   чекаута master, штаб не пушит в master напрямую.

## Bootstrap (разово, до тикета 01)

- [x] `git init` в `pet-care-tracker/` (ветка master), `.gitignore`
- [x] Первый коммит: `#00 docs: спека, ADR, архитектура, глоссарий, тикеты, команда`
- [x] GitHub-репозиторий https://github.com/l2cri/pet-care-tracker, пуш master
- [ ] Settings → Branches: защита master от прямых пушей (нужен PR); Merge-метод —
      только «Squash and merge» (Allow squash merging оставляем, merge commit и
      rebase можно выключить)
- [x] Settings → Pages: Source → GitHub Actions (включено через API: build_type=workflow)
- [x] CI (GitHub Actions: npm ci + vitest + Pages) — это тикет 01

## Известные трения (и почему это ок)

- Сквош съедает пошаговую историю сессии в master — она сохраняется в PR и в
  чек-боксах тикета; журнал вех важнее деталей шагов (принцип 4).
- Спавн субагентов иногда блокируется платформой — обход через general-purpose
  под явным чартером (раздел выше).
- Worktree и главный чекаут делят один `.git` → фоновых сюрпризов нет, но
  одновременный `git gc`/rebase в двух папках не запускайте.
